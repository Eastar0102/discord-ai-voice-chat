# 실험과 결과

[English](RESULTS.md) · **한국어** · [← README](../README.ko.md)

이 파이프라인의 설계 결정은 모두 같은 순서로 내렸습니다. 실제 음성 세션에서 실패를 먼저 재고, 고친 뒤 다시 쟀습니다. 이 문서는 그 숫자들을 모은 것입니다. 각 결정의 이유는 [ARCHITECTURE.ko.md](ARCHITECTURE.ko.md#설계-메모--틀리기-쉬운-것들)에 있습니다.

**환경.** 윈도우 PC 한 대, 12GB 소비자용 NVIDIA GPU. 따로 적지 않으면 전부 로컬입니다.
- STT: faster-whisper large-v3-turbo
- LLM: Ollama로 돌린 7B~8B 모델
- TTS: GPT-SoVITS v2Pro

측정 시기는 2026년 9~10월입니다. 이 숫자로 말할 수 있는 것과 없는 것은 [방법과 한계](#방법과-한계)에 정리했습니다.

## 한눈에

| | 결과 |
|---|---|
| 체감 지연 (말이 끝난 순간 → 첫 소리) 중앙값 | 전부 로컬로 돌린 98턴 실사용 세션에서 **2.49초** |
| prefetch + 캐시 친화 배치의 첫 토큰 (MoE, CPU 배치) | **2.59초 → 0.37초** |
| 대답 안에 `(pass)`를 쓰게 해서 "대답할까?" 판단 | **286번 중 0번** 작동 → 규칙 + 안전장치 달린 판정으로 교체 |
| 기억 정리 판정을 "버릴까?" 대신 "무엇에 관한 문장인가?"로 물음 | 놓친 쓰레기 **25/41 → 1/41**, 버린 진짜 사실 **6~9/20 → 1~2/20** |
| 현재 시각을 프롬프트 맨 끝으로 | 날짜·시각 퀴즈 **4/8 → 12/12** |
| 화면 OCR, 글자 높이 24px 이상 | 글자 정확도 **99%** (기본 16px 에디터는 87%) |

## 1. 지연

### 시간이 어디서 드나

![첫 소리까지 단계별 시간](images/ttfa.svg)

| 단계 | 초 |
|---|---|
| 말끝 기다림 (말이 끝났다고 판단) | 0.60 |
| 프롬프트 조립 (기억·세계관 검색 포함) | 0.06 |
| LLM 첫 토큰 (약 2,100토큰 prefill 0.36초 포함) | 0.68 |
| 처음 읽을 수 있는 조각이 나올 때까지 | 0.34 |
| 첫 조각 TTS | 1.08 |
| **합계** | **2.76** |

큰 몫은 TTS와 말끝 판단입니다. 모델 자체는 주된 비용이 아닙니다.

### 고치기 전과 후

![지연 개선 전후](images/latency-fixes.svg)

| 바꾼 것 | 지표 | 전 | 후 |
|---|---|---|---|
| 서버 기동 워밍업 때 성격 프롬프트·기록을 미리 prefill | 띄운 뒤 첫 대답 | 16.5초 | 2.06초 |
| 화면을 본 뒤 비전 모델 내리기 | 대답마다 체감 지연 | 13.84초 | 2.65초 |
| GPT-SoVITS에 요청을 하나씩 | 14자 조각 합성 | 13~30초, 대답마다 끊김 3번 | 1.1~1.5초, 끊김 0 |
| llama.cpp `--cpu-moe`에 `-ub 4096` | 첫 토큰 | 8.3초 | 2.6초 |
| 첫 문장을 쉼표에서도 자르기 | 첫 조각 합성 최악값 | 5.7초 | 3.4초 |
| 턴마다 바뀌는 칸을 기록 뒤로 | 첫 토큰 (MoE) | 2.59초 | 1.6초 |
| … + 부분 전사로 prefetch | 첫 토큰 (실제 경로) | 2.59초 | 0.37초 |
| 말하는 동안 프롬프트 미리 먹이기 | 첫 조각 준비 (8B) | 1.06초 | 0.55초 |
| GPT-SoVITS가 클립 앞뒤에 붙이는 무음 자르기 | 조각 이음매의 무음 | 0.45초 | 0.16초 |

GPT-SoVITS의 `parallel_infer`는 어느 길이에서나 *끄는* 쪽이 빨랐습니다:

| 글자 수 | 켬 | 끔 |
|---|---|---|
| 10~16 | 1.19초 | 1.08초 |
| 25~35 | 2.76초 | 2.11초 |
| 50~70 | 5.18초 | 4.15초 |

### 디스코드 음성에서 말끝 잡기 (실제 646턴)

| 말끝 경로 | 비율 | 지연 중앙값 |
|---|---|---|
| 패킷이 끊김 (디스코드가 보내기를 멈춤) | 48% | 0.92초 |
| 침묵 시작 + 부분 전사가 문장으로 끝남 | 31% | 0.32초 |
| 침묵 600ms | 22% | 0.60초 |

디스코드는 말이 끝난 뒤 0.5초쯤 침묵을 더 보내다 끊습니다. 그래서 고전적인 침묵 규칙은 거의 채워지지 않습니다. 가장 흔한 경로가 가장 느렸고, 생각하느라 멈춘 말을 자르는 것도 이 경로였습니다. 그래서 끊김 기준을 0.4초로 두되, 부분 전사가 이어질 말처럼 끝나면("아니 근데…") 1.0초까지 기다립니다.

### 모델 고르기 — 실제 24턴 재생

| 모델 | 실행 방식 | 첫 토큰 | 속도 | VRAM |
|---|---|---|---|---|
| 7B (A.X-4.0-Light 기반) | Ollama, Q4_K_M | 0.81초 | 85 tok/s | 5.0GB |
| Kanana-2-30B-A3B (MoE) | llama.cpp `--cpu-moe -ub 4096` | 2.59초 | 42 tok/s | 2.8GB |
| Kanana-2-30B-A3B (MoE) | `--n-cpu-moe 40` | 2.25초 | — | 5.8GB |
| Qwen3.6-35B-A3B (MoE) | `--cpu-moe`, 원래 배치 | 2.73초 | — | — |

독해 문제 15개 × 5회에서는 30B MoE가 7B를 이겼습니다 (**66/75 대 57/75**). 그런데 실제 34턴 세션에서는 쓸 수 없었습니다:
- 말할 차례 판정이 1:1 대화에서 **13번**이나 침묵했습니다.
- 현재 시각 줄을 대답으로 **4번** 읽었습니다.

**모델 교체는 질문 세트가 아니라, 판정까지 포함한 대화 재생으로 판단해야 합니다.**

## 2. 말할 차례 — 대답하지 *말아야* 할 때

| 방법 | 측정 대상 | 결과 |
|---|---|---|
| 페르소나 모델에게 대답 안에 `(pass)`를 쓰게 함 | 실제 발화 286개 / 고정 케이스 10개 | **0번** / **0/10** |
| 성격을 뺀 별도 Y/N 판정 | 고정 케이스 | 조용해야 할 때 **10/10** 조용했지만, 자기에게 한 말의 **절반**을 삼킴 |
| 같은 판정을 실제로 대답한 발화에 | 100개 | **14개**를 침묵시켰을 것 |
| `must_answer`(이름·2인칭·질문 어미) 뒤에 판정 | 잘못 넘긴 비율 | **18% → 8%** |
| 규칙 먼저, 사람 수를 주 신호로 | 1:1 발화 489개 | 규칙이 침묵시킨 것 **1개** |
| 규칙 + 안전장치 판정, 처음부터 끝까지 | 잘못 대답했던 8개 / 실제 대답 60개 | **5/8** 이제 넘김 · **3/60** 넘김 (모두 넘겨도 되는 말) |

**안전장치 넓히기.** 질문 어미 두 개(`까`, `냐고`)를 넣기 전에 기록에 대고 검증했습니다. 기록 841줄에서 새로 강제로 답하게 되는 **11줄**은 전부 진짜 질문이었습니다. 넘겨야 할 21개 중 새로 걸리는 것은 **0개**였습니다.

**이름으로 둔갑한 소음.** Whisper 핫워드는 소음도 그 단어로 바꿉니다. 아는 이름 두 개 이상으로만 된 전사를 버리면, 실제 발화 653개 중 **5개**가 빠지고 그 5개가 정확히 가짜였습니다. Whisper 확신도도 둘을 가릅니다:

| | 평균 로그 확률 |
|---|---|
| 진짜 말 | 약 −0.22 |
| 핫워드 소음 | −0.65 ~ −0.96 |

그래서 기억 추출의 확신도 하한을 그 사이인 −0.6에 뒀습니다.

| 기록엔 "(아무도 말하지 않음)", 모델엔 "(네가 먼저 말을 꺼낸다)" | 3/3 "조용하네요, 질문 있으세요?" | 3/3 진짜 화제 |

## 4. 장기 기억

| 실험 | 결과 |
|---|---|
| 임베딩 거리로 갱신 판단 | "골드 2" → "플래티넘"이 거리 **137**이라 둘 다 남음 → 기존 사실을 보여 주고 추가/교체/무시를 고르게 함 |
| 관련도 기준선 | 관련 있는 최상위 **60~100**, 무관하게 끌려온 것 **130~166** → 기준 **120** |
| 칸 배분: 최근 6 : 관련 2 → 관련 우선 + 최근 바닥 | "규칙 다시 알려줘"에 올라오는 게임 규칙: 13개 중 **2 → 5** |
| 한 세션에 맞춰 쓴 낱말 필터를 다음 세션에 | 쓰레기 사실 **0/30** 거름 |
| 판정을 "버릴 것을 고르라"로 | 진짜 사실 **6~9/20**을 "사소하다"며 버림 |
| 판정을 "무엇에 관한 문장인가"로 (3회) | 쓰레기 놓침 **1/41** · 진짜 사실 버림 **1~2/20** |
| 낱말만으로 | **25/41** 놓침 |
| 같은 판정을 로컬 7B 베이스로 | 진짜 2/5 버림 · 쓰레기 4/6 놓침 (쓸 수 없음) |
| 자기 설정 필터 ("취향"으로 저장됐지만 아니었던 것) | 11/11 의도대로 분류. 저장된 자기 설정 7개 중 진짜는 1개 |
| 말한 날 당일 날짜를 일정으로 셈 | 저장된 "일정" 8개 중 6개가 끝난 일이었음 → 고침, 진짜 일정 2개는 유지 |

## 5. 눈 — 화면과 링크

![글자 높이별 OCR 정확도](images/ocr-glyph.svg)

| 화면 글자 높이 | 10px | 17px | 21px | **24px** | 26px | 34px |
|---|---|---|---|---|---|---|
| 글자 정확도 | 53% | 87% | 91% | **99%** | 97% | 96% |

| | 시간 | VRAM | 한글 | 그림 이해 |
|---|---|---|---|---|
| 윈도우 내장 OCR | 2560×1440에서 1.7초 | 0 | 5/5 정확 | 못 함 |
| qwen3-vl:4b | 8~21초 | 3.0GB | 비슷하게 | 함 |

둘은 하는 일이 달라서, 화면 보기는 둘 다 씁니다.
- **해상도는 용도마다 다르게.** OCR용으로 2560 → 1280으로 줄였더니 읽힌 줄이 **220 → 39**로 줄었습니다. 이 실수 때문에 "비전 모델이 한글을 못 읽는다"는 잘못된 결론을 낸 적이 있습니다.
- **글자 먼저, 설명은 나중에.** 전체 보기는 약 36초 걸리지만, OCR 글자는 약 2초 만에 프롬프트에 들어갑니다. 설명은 그동안 따로 만들어집니다.

## 6. 전사 모드 프리셋

오디오 2.3초 기준:

| 프리셋 | 모델 | VRAM | 시간 |
|---|---|---|---|
| fast | large-v3-turbo, int8 | 약 1.6GB | 0.3초 |
| accurate | large-v3, beam 5 | +3.6GB | 0.4초 |
| max | large-v3, beam 8 + 온도 폴백 | +3.6GB | 0.6초 |
| cpu | large-v3, CPU int8 | 0 | 5.7초 |

전사하는 동안 어시스턴트의 LLM과 TTS를 내려놓아야 `accurate`가 들어갔습니다. 그대로 두면 12GB 카드에 13.9GB가 필요했습니다.

## 방법과 한계

- **실제 세션, 비공개 데이터.** 숫자 대부분은 개발자의 디스코드 세션과 거기서 쌓인 대화 기록에서 나왔습니다. 평가 스크립트는 그 기록을 읽고 실제 발화를 담고 있어서 이 저장소에 **포함하지 않았습니다**. 저장소만으로 재현할 수는 없습니다.
- **작은 표본.** 많은 비교가 n = 4~20이라 방향을 보는 숫자이지 통계적 유의성은 없습니다. 재생이나 실사용으로 한 번 더 확인한 결과는 그렇다고 적었습니다.
- **한 대의 기계.** 지연은 GPU, VRAM 여유, 같이 올라간 것에 따라 달라집니다. 절대 초보다 결과의 모양(어느 단계가 크고 무엇이 듣는지)이 더 잘 옮겨집니다.
- **기록으로는 한쪽 오류만 잰다.** 기록된 줄은 전부 대답한 것이라, 말할 차례 규칙이 잘못 *침묵*시키는 것은 보여도 잘못 *대답*하는 것은 보이지 않습니다. 그쪽은 실사용 세션에서 왔습니다.
- **벤치마크는 실사용의 실패를 놓친다.** 가장 분명한 예가 위의 30B 모델입니다. 질문 세트에서는 이겼고 대화에서는 무너졌습니다.
